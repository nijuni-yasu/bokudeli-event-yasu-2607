作成日: 2026-10-16。本書は `14_競合調査` の調査(事実)を受けて、**「ユーザー獲得・継続率向上のために、いま実装を進めるべき機能はどれか」を決める**ための判断文書である。調査文書と違い、優先度と推奨を書く。根拠の強さは調査文書の判定を引き継ぎ、[事実] は出典で確認できたこと、[推測] は執筆者の判断である。自社の実装状況は `origin/development`(v2.14.0 相当、2026-10-16)のコードと Issue で確認した。

## 0. 結論(先に読む)

**課題は「集客力」である。** 調査の結論は、集客に効く機能の根拠は競合各社でもほとんどが相関と自社主張であり、成長を決めたのは個別の機能ではなく「参加者が次の参加者と幹事を連れてくるループ」と「供給側(幹事・店)への伴走」だった([有力機能の評価](../30_機能比較/03_有力機能の評価.md) §要約)。Shokujii の現状は、ループの部品が個別には揃っている(共有ボタン、自動メンバー化、イベントコピー、イベント後アンケートメール、ともだち蓄積)のに、**部品同士がつながっておらず、どの経路から参加者が来たかも測れていない**。

**推奨: 単発の機能ではなく、計測基盤(柱 0)と次の 4 本柱を「集客ループ v1」として一括で意思決定し、計測基盤から順に着手する。**

| 柱 | 狙い | 含める機能(§5 の ID) | 工数目安 |
| :-- | :-- | :-- | :-- |
| **柱 0 計測** | 経路別の申込を測れるようにする(以降すべての前提) | F-04 共有・招待・ダイジェスト経由の計測 | S |
| **柱 1 招待・共有ループ** | 参加者が他の参加者を呼ぶ。幹事の集客労力を減らす。SNS に出す素材を渡す | F-01 たべとも招待、F-02 紹介リンクと「誰が連れてきたか」の可視化、F-03 SNS 投稿文の拡張 | M + S〜M + S |
| **柱 2 イベント後ループ** | 参加者が次も参加する。参加者が次の幹事になる | F-06 イベント後ページ、F-07 前回参加者への優先案内と次回予告、F-08 「次は自分が幹事」CTA、F-22 参加回数上位への主催打診(運用) | M + M + M + 運用 |
| **柱 3 幹事の継続(シリーズ開催)** | 幹事が続けやすい。開催が勝手に始まる | F-17 シリーズ開催の自動パイプライン、F-18 告知スケジュール自動化、F-19 幹事の「次にやること 1 件」 | L + M + S |
| **柱 4 発見面の最小版** | 参加ハードルを下げる。幹事の集客力を上げる(在庫が出てから) | F-12 トップの「今週」「締切間近」「近くの公開食事会」と related、F-13 週次ダイジェストのエリア・タグ別化 | M + M |

**着手順は 柱 0 → 柱 1 → 柱 2 → 柱 3 → 柱 4。** 理由は、(a) 計測がないと他社に定量値がない領域で自社の根拠を作れない、(b) 柱 1・2 は既存の仕様書・基盤(たべとも、イベント後メール、イベントコピー)の延長で工数が小さく転換に近い、(c) 柱 3 は効果が大きいが工数が最大で、柱 1・2 で幹事が増えてから効く、(d) 柱 4 は公開イベントの在庫が薄いうちに作ると空のフィードになる([露出獲得施策 §6.5](../../13_成長・露出/01_露出獲得施策.md#65-誤優先意図的に後ろに下げる))、である [推測]。

**今期は見送る(理由は §7):** 報酬型の紹介(Posh Kickback 型)、参加者向けサブスク・月額会員、プラットフォーム内の有料ブースト、エリア×ジャンルの pSEO ハブ、卓編成・マッチング、アカウント不要の決済、公開の星評価レビュー。

意思決定の記録(採用・却下・未決)は §9 に ADR 形式で置く。**人が決める未決事項は 5 件**(§9.3)で、いずれも実装着手を止めるものではない。

## 1. 前提:何が課題で、調査は何を言ったか

### 1.1 Shokujii の集客の構造

Shokujii は、幹事がイベントを立て、参加者がメニューを事前注文して参加する構造が強い([露出獲得施策 §2.2](../../13_成長・露出/01_露出獲得施策.md#22-プロダクト上の前提露出の最短経路))。参加者の入口は三つに分かれる([参加者獲得](../10_概観/03_参加者獲得_機能と施策.md) §三つの入口)。

| 入口 | 意味 | Shokujii の現状 [事実] |
| :-- | :-- | :-- |
| 共有(招待) | 幹事・参加者が自分の輪にリンクを送る | 共有ボタン(LINE・X)・OGP・QR・チラシはある(SH01・SH02・SH07)。注文完了時のたべとも招待は仕様書のみ(#1249・#953)。紹介者の追跡・UTM はない(SH04・OP10) |
| 発見(検索・フィード・推薦) | 知らない人が見つける | 公開コミュニティ一覧・sitemap・JSON-LD・「人気のイベント」(参加人数順)はある。都市×カテゴリのハブ・related・パーソナライズはない(DS02・DS04・DS07)。検索流入は 3 か月で約 645 クリック(2026-07) |
| 継続(フォロー・購読・メンバー化) | 一度来た人が戻る | 注文時の自動メンバー化、新着メール、週次ダイジェスト、LINE 一斉配信、イベント後アンケートメール、イベントコピー・繰り返しはある(CR01・CR02・OP02・JN12)。前回参加者への優先案内・次回予告・参加者→幹事の導線はない(CR03・機能外) |

ツール型(Luma・Partiful)は共有、マーケットプレイス型(Eventbrite・DICE)は発見に重心があり、ツール型は発見面を後から足した [事実]。Shokujii は幹事主導のツール型に近く、**共有と継続を先に、発見を後に**置くのが調査と整合する [推測]。

### 1.2 調査が示した、効いたもの・効かなかったもの

[有力機能の評価](../30_機能比較/03_有力機能の評価.md) の要点を、本書の判断に関わる範囲で再掲する。

| 根拠の強さ [推測] | 内容 [事実] | 本書での扱い |
| :-- | :-- | :-- |
| 強(経路の存在) | Eventbrite の主催者の約 70% は他者のイベント参加(34%)か口コミ(36%)で知った(10-K FY2018)。転換率の公開値はない | 柱 2 の F-08・F-22 の根拠。転換率は自社で測る |
| 強 | 供給側(幹事・店)への個別アウトリーチ・伴走(DICE・ストアカ・Ticket Tailor 等)。機能ではなく人の作業 | 機能の外。F-22(運用)と、柱 3 で幹事の継続負担を下げることで補う |
| 中 | 口コミ・バイラル(Luma「ほぼ完全に口コミ」、Partiful)。Eventbrite の共有 1 回あたり売上 $1.78(2010 年、自前計測) | 柱 1 の根拠。k-factor はどの社も非公開 |
| 中 | 自動メンバー化・通知メール(connpass の会場の 8〜9 割が通知経由 [二次]、Peatix の発見機能経由 約 15%) | 自社は ✅。柱 2・柱 4 で範囲を広げる |
| 中 | 発見面(Eventbrite の発券 30% 超が発見経由、DICE 41%)。帰属比率であって増分ではない。公開在庫の厚さが前提 | 柱 4。在庫が薄いうちは最小版 |
| 中(自己申告) | 定期・会員・コミットメント(Timeleft の月平均利用 1.4→2.2 回、트레바리 再登録 70% 超) | サブスクは見送り。「定例開催に参加者を紐づける」設計(柱 3)で代替 |
| 負(強) | 幹事・無料イベントへの課金(Eventbrite 2023、Meetup)。離脱は回復しなかった | 幹事無料は維持(AC01 ✅) |
| 負 | 広告での都市量産(Timeleft 325→162 都市)、固定費を抱えた自社運営(Dinner Lab) | 密度指標(§6)で拡大を縛る。運営主催は固定費ゼロの範囲 |
| なし | 検索・絞り込み・ブックマーク・ウェイトリスト・QR 受付・レビューなどの標準装備 34 機能のうち 17 機能は根拠が見つからない | 「無いと不利」の穴は、根拠のある柱の後に回す |

**含意 [推測]:** 標準装備の穴(ウェイトリスト、地図検索、QR 受付など)を埋めるより、根拠が中以上の「ループ」を先に閉じる。他社に定量値がない以上、**自社で測れる形で作る**ことが機能そのものと同じくらい重要である。

### 1.3 Timeleft から学ぶ、日本の食事会で参加者が離れる理由

[Timeleft 調査](../70_Timeleft調査/04_運営とユーザーの声.md) §継続のパターンでは、やめる理由として「店・顔ぶれの繰り返し」5 件、「課金・サポート不信」約 5 件、「欠席・人数不足」3〜4 件、「費用対効果」約 3 件が挙がり、再び参加するきっかけは「別フォーマット」「初回の満足度が高ければそのまま次を予約」だった [事実]（件数は読んだ範囲で代表性はない）。日本の自己集計 1 件では、会った相手との関係は「連絡先のみ 60%、その会限り 20%」である。

**含意 [推測]:** 継続は「初回の直後に次の予約がある」ことと「会った人とまた会える導線」で決まる。Shokujii は幹事が常設のコミュニティを持つので、Timeleft が持てない「同じ幹事・同じ仲間の 2 回目」を作れる。これが柱 2・柱 3 の位置づけである。

## 2. 評価の物差し

候補は次の 5 軸を 1〜3 で採点し、合計で並べた。採点はすべて [推測] で、工数は S/M/L の目安(定義は [SEO 対策タスク](../../12_SEO対策/01_SEO対策_タスク.md) と同じ)を 3〜1 に読み替えた。合計は順位の目安であり、最終判断は §5 の柱の組み合わせで行う。

| 軸 | 3 | 2 | 1 |
| :-- | :-- | :-- | :-- |
| 集客への効き | 新規の参加者・幹事を直接増やす | 既存ユーザーのリーチを広げる | 間接的 |
| 継続への効き | 2 回目の参加・開催に直結 | 満足度・関係の維持に効く | 間接的 |
| 根拠(調査) | 強・中 | 弱 | なし |
| 既存資産との適合 | 仕様書または基盤があり延長で作れる | 一部ある | 新規設計 |
| 工数(逆) | S | M | L |

ユーザー(依頼者)が挙げた 11 の観点は、次の記号で各候補に付ける。

| 記号 | 観点 |
| :-- | :-- |
| P1 | 参加者同士の交流を促進し、満足度を上げる |
| P2 | 参加者の参加ハードルが下がる |
| P3 | 参加者が継続して参加したくなる |
| P4 | 参加者が SNS に投稿したくなる |
| P5 | 参加者が他の参加者を呼びたくなる |
| O1 | 主催者が継続して主催したくなる |
| O2 | 主催者が継続して主催しやすくなる |
| O3 | 主催者の集客力が上がる |
| O4 | 主催者の集客する労力が減る |
| O5 | 主催者が SNS に投稿したくなる |
| O6 | 主催者と参加者の交流を促し、満足度を上げる |

## 5. 推奨する実装セット(意思決定の対象)

各機能は「MVP の範囲」「根拠」「成功指標」「既存資産」「リスク」を書く。工数は目安で、Issue 分割時に見積もり直す。

### 柱 0 計測(F-04)

- **MVP:** (1) 共有ボタン・招待・ダイジェスト・LINE 配信のリンクに経路パラメータ(`utm_source` / `utm_medium` 相当)を付ける。(2) 申込(注文確定)時に、セッションの経路パラメータを**注文ドキュメント(`member_orders`)単位**に不変の値として記録する。会員ドキュメントには保存しない(上書きすると過去の帰属が消え、保持すると後続の申込が最初の経路へ誤帰属するため)。帰属は last-touch(最後に踏んだ経路)とし、経路パラメータの有効期間は仮に 7 日(ブラウザ保存)とする。(3) 共有ボタンの押下・コピーをクライアントイベントとして記録する。(4) 運営向けに「経路別の申込数」を集計できる最小のクエリ(support 画面か BigQuery/集計 Function)。
- **根拠:** 他社は紹介経由比率・k-factor・ゲスト→主催者転換率を公開していない [事実]。自社で測らない限り、以降の柱の効果を判断できない。
- **成功指標:** 経路別の申込比率が出せること(機能自体の KPI はない)。
- **既存資産:** 短縮 URL(#2322、未実装)と設計を合わせる。OGP は既存。
- **リスク:** 経路パラメータは個人情報ではないが、紹介者 ID(F-02)を URL に載せる場合は推測不能な値にする。
- **工数:** S。

### 柱 1 招待・共有ループ(F-01・F-02・F-03)

**F-01 たべとも招待**

- **MVP:** 注文完了モーダルに、ご一緒した回数順のたべとも(最大 10 名)をチェックで選んで招待メールを送る([友人招待機能](../../03_参加者獲得/02_友人招待機能.md) の Phase 1 をそのまま採用)。LINE 共有は既存の共有ボタンへ誘導し、招待文面に F-03 の文面を流用する。
- **根拠:** SH03(弱)。Luma は登録直後に友人招待を促し、Partiful・Posh も招待リンクを主経路とする [事実]。転換率は非公開。
- **成功指標:** 招待送信率(注文完了のうち招待を送った割合)、招待→申込率、1 イベントあたりの招待経由申込数。
- **既存資産:** 仕様書あり、`userFriends` store・`getUserFriends` Callable あり、Issue #1249・#953。
- **リスク:** 招待メールのスパム性(同意・配信停止)。受信者が未登録の場合の着地(未ログイン閲覧の厚み D5-2 と連動)。
- **工数:** M。

**F-02 紹介リンクと「誰が連れてきたか」の可視化**

- **MVP:** 参加者・幹事が共有・招待したリンクに紹介者トークンを付け、そのリンク経由の申込に紹介者を記録する。幹事のイベント管理画面に「紹介者別の申込数」を表示する(参加者本人には出さない)。報酬は付けない。
- **根拠:** SH04(弱)。Luma Event Referrals は報酬なしで可視化し、幹事に上位紹介者への感謝・早期アクセスを勧める [事実]。Posh の Kickback(報酬型)は原資・返金・不正対策が要り、Ticket Tailor では紹介インセンティブが効かなかった [事実]。
- **成功指標:** 紹介者付きリンク経由の申込比率、紹介者 1 人あたりの申込数の分布(上位紹介者の特定)。
- **既存資産:** F-04 の経路記録に紹介者 ID を足す形。
- **リスク:** 紹介者の表示は幹事のみに限定する(参加者間の序列化を避ける)。自己紹介(自分のリンクで自分が申し込む)は除外する。
- **工数:** S〜M。

**F-03 SNS 投稿文の拡張**

- **MVP:** 既存の `shareSnsButton`(X 投稿文・コピー文を生成)を土台に、(1) LINE 向けの短文テンプレート、(2) メニューの見どころと残席(少ないときのみ)の差し込み、(3) URL への F-04 の経路パラメータ付与、(4) 幹事の管理画面に「告知文をコピー」導線、を足す。新規の文面生成 util は作らず、既存 util の引数とテンプレートを拡張する。LLM は使わない。
- **根拠:** SH02(中)。Eventbrite の共有 1 回あたり売上 $1.78(2010 年、自前計測)、ZAIKO の販売の約 4 割が本人の Twitter 経由 [幹部発言]。幹事の告知コストを下げる(A-05 は確度高)。
- **成功指標:** コピー押下率、コピー後のリンク経由申込(F-04 で計測)。
- **既存資産:** `shareSnsButton`(X 投稿文・コピー文の生成、LINE・X・Facebook の共有)、OGP、`event_sns_hash_tag`。
- **リスク:** 残席の表示は社会的証明と逆効果(空席を煽る)になりうるため、残席が少ないときだけ出す。
- **工数:** S。

### 柱 2 イベント後ループ(F-06・F-07・F-08・F-22)

**F-06 イベント後ページ**

- **MVP:** イベント終了後、参加者がメールから着地する専用ページを作る。内容は (1) お礼と写真(アルバムのサムネイル)、(2) 次回予告(F-07 で幹事が設定した候補日、未設定なら「次回のお知らせを受け取る」)、(3) 「また会いたい」反応(同席者に対する非公開の 1 タップ。集計は幹事と運営のみ、本人には件数だけ)、(4) 「次は自分が幹事」(F-08)。既存のアンケートメールの着地をこのページに変える。
- **根拠:** JN12 は ✅ だが、Timeleft の継続調査では「初回の直後に次の予約がある」ことが再参加のきっかけだった [事実]。会った後の関係が続かない(連絡先のみ 60%)という隙(B3、根拠は弱)。
- **成功指標:** イベント後ページの到達率、「また会いたい」の実施率、ページからの次回申込率・幹事 CTA 押下率。
- **既存資産:** `eventConclusionMail`(SendGrid テンプレート)、`PublicAlbumGallery`、イベントチャット。
- **リスク:** 相互評価は内気な参加者の負担になる(Timeleft の Impressions への抵抗 [声])。公開しない・件数だけ・任意を守る。
- **工数:** M。

**F-07 前回参加者への優先案内と次回予告**

- **MVP:** (1) 幹事がイベント終了時に「次回候補日」を 1 つ入力できる(F-17 のシリーズ設定があれば自動)。(2) 次回イベントに「前回イベント ID」を持たせる(イベントコピー・繰り返し作成で作ったイベントはコピー元を自動で前回とし、手動作成時は幹事が選ぶ)。同じコミュニティが複数の食事会を並行開催しても、前回参加者を一意に特定できるようにする。F-17 の `series_id` 導入後はシリーズ内の直前イベントに置き換える。(3) 次回イベントの公開時に、前回参加者へ全体公開の N 時間前に先行メールを送る(N は幹事が選ぶ、既定 24 時間)。LINE は含めない(既存の LINE 配信は公式アカウントの全フォロワーへの `broadcast` のみで、対象者を絞った送信経路がない)。(4) 先行案内のリンクは F-04 の経路付き。
- **根拠:** CR03 は根拠なしだが、CR02 の連鎖(connpass・Doorkeeper・Peatix の自動メンバー化と通知)が中 [事実]。Timeleft B3 の最小検証(終了後に次回候補日を前回参加者へ優先案内)と一致。
- **成功指標:** 先行案内→申込率、初回参加者の 30 日・90 日再参加率。
- **既存資産:** 新着メール・自動メンバー化・レター。イベントコピー(`eventCopy`)のコピー元情報。
- **リスク:** 先行枠が内輪化を進める(新規が入れない)。先行は「案内」であって「枠の確保」ではない設計にする。LINE での個別配信は、アカウント連携・同意・対象者への push/multicast を含む別スコープとして扱う。
- **工数:** M。

**F-08 「次は自分が幹事」CTA と設定コピー**

- **MVP:** イベント後ページとマイページの参加履歴に「同じ設定で自分の食事会を開く」を置き、押すと (1) コミュニティがなければ作成ウィザードへ、(2) あれば参加したイベントの店・メニュー構成・説明を下書きにコピーして作成画面へ。コピー元の幹事情報・参加者は含めない。
- **根拠:** Eventbrite の主催者の約 70% が他者のイベント参加か口コミで知った(10-K FY2018)[事実]。導線機能の効果は非公開。
- **成功指標:** CTA 押下率、押下→初回公開率、参加者→幹事転換率(月次)。
- **既存資産:** コミュニティ作成ウィザード。既存の `eventCopy` Callable は**そのまま流用しない**(呼び出し元にコピー元コミュニティの manager 権限を要求し、コピー先を同じ `community_id` に固定し、幹事の氏名・電話・メール・請求先まで複製するため、参加者からの呼び出しは拒否され、権限だけ緩めると他人のコミュニティへの作成や PII の複製が起きる)。参加者向けは、コピー先コミュニティの管理権限を検証し、公開フィールド(店・メニュー構成・説明・画像)だけを許可リストで移す**別の Callable** として設計する。
- **リスク:** コピーできる範囲(公開イベントのみ、店の承認が要る)を明確にする。幹事の負担が重いと転換は低い(日本の食事会の幹事は負担が大きい [推測])ので、柱 3 とセットで効く。
- **工数:** M(別 Callable と権限検証を含むため)。

**F-22 参加回数上位への主催打診(運用)**

- **内容:** 月次で参加回数上位(たとえば 3 回以上)の参加者を抽出し、運営または所属コミュニティの幹事から「次は幹事をやってみませんか」と個別に打診し、初回は告知文・店の確保・当日まで伴走する。
- **根拠:** 供給側への個別アウトリーチ・伴走(強)。ストアカの地域コーディネーター、Ticket Tailor の電話、트레바리 の説得 [事実]。
- **成功指標:** 打診→初回開催率、初回開催した幹事の 2 回目開催率。
- **工数:** 開発なし(参加回数の集計は既存)。F-20 の月次レポートで抽出を自動化するのは Phase 2。

### 柱 3 幹事の継続(F-17・F-18・F-19)

**F-17 シリーズ開催の自動パイプライン**

- **MVP:** (1) イベントに `series_id` を持たせ、シリーズ設定(店・メニュー構成・締切日数・定員・説明・開催周期・祝日スキップ)をコミュニティ配下に保存する。(2) 前回イベントの終了(または幹事の任意のタイミング)で次回を下書き生成し、幹事へ通知する。(3) オプトインで「承認後 N 時間で自動公開」「下書き放置 N 日で確認メール」を選べる。(4) 連続して最小催行人数未達ならシリーズを一時停止して見直しを提案する(サーキットブレーカー)。予約申請の自動送信(O-08)は Phase 2。
- **根拠:** 売上は高頻度の少数主催者に集中する(Eventbrite の有料クリエイターの 13% が有料チケットの約 60% [要約])[事実]。Doorkeeper は自動メンバー化と定期開催でメンバーが継続的に増えた [事実]。「何もしなくても勝手に始まる」が主催自動化の目標。
- **成功指標:** シリーズ設定を持つコミュニティ数、幹事の 2 回目・3 回目開催率、幹事 1 人あたり月間開催数、自動生成した下書きの公開率。
- **既存資産:** イベントコピー・繰り返し作成(一括コピー・下書きまで)、最小催行人数・自動中止(実装済み)、作成の初期値の仕様。
- **リスク:** 自動化の空回り(誰も来ない回を量産)。オプトイン既定・サーキットブレーカー・店の承認を外さないことで抑える。幹事の自動注文(O-06)はスコープ外。
- **工数:** L。

**F-18 告知スケジュール自動化**

- **MVP:** シリーズまたは単発イベントに告知スケジュール(公開時・7 日前・3 日前・前日・締切後)をテンプレートで持ち、レター・メールをスケジューラで送る。LINE は含めない(既存の LINE 配信は全フォロワーへの `broadcast` のみで、イベント別・対象者別に送れない。個別配信は F-07 と同じ別スコープ)。文面は F-03 のテンプレートを流用し、幹事は ON/OFF と文面の上書きだけ行う。
- **根拠:** CR01(中)。connpass の通知メール経由が会場の 8〜9 割 [二次]、Peatix の発見機能経由 約 15% [二次]。A-04 は確度高。
- **成功指標:** 自動告知経由の申込比率(F-04)、幹事の手動レター送信数の減少。
- **既存資産:** レター、未注文リマインド(`remindUnorderedMail`)、締切メール。
- **リスク:** 配信量の増加による配信停止率の上昇。コミュニティ単位の配信停止と頻度の上限を置く。
- **工数:** M。

**F-19 幹事の「次にやること 1 件」**

- **MVP:** 幹事のコミュニティ管理画面の先頭に、未公開の下書き・承認待ち・未告知・未注文(幹事自身)・次回未設定を優先順に 1 件だけ出す。
- **根拠:** U-02(確度高)。数字や次の一手が見えることは「次も開く」動機 [推測]。
- **成功指標:** 表示→実行率、下書き放置日数の短縮。
- **工数:** S。

### 柱 4 発見面の最小版(F-12・F-13)

**F-12 トップの「今週」「締切間近」「近くの公開食事会」と related**

- **MVP:** トップに「今週開催」「締切間近」の 2 列を足し、位置情報または登録エリア(F-13 の設定)で「近くの公開食事会」を出す。イベントページ下部に同エリア・同タグの公開イベント(related)を 3 件。パーソナライズはしない。**すべてのクエリに `is_public == true` と `enterprise_id == null` の両方を必須条件にする**。PF と enterprise は同じイベントコレクションを共有し、enterprise イベントも `is_public: true` を取り得るため、`is_public` だけでは社内イベントが user 側へ露出する(既存の `user/src/pages/index.vue` と同じ条件)。
- **根拠:** DS04・DS07(中、帰属比率)。Eventbrite の発券 30% 超が発見経由、Peatix 約 15% [自社主張]。公開在庫が前提 [推測]。
- **成功指標:** 発見経由(トップ・related)の申込比率(F-04)、1 PV あたりの他コミュニティへの遷移率。
- **前提:** 公開イベント(`is_public`)の在庫。在庫の閾値(たとえば常時 10 件以上)を着手条件にする [推測]。
- **工数:** M。

**F-13 週次ダイジェストのエリア・タグ別化**

- **MVP:** (1) ユーザー設定に「食事会を探すエリア」(都道府県と市区町村、任意)を追加する。現在のユーザースキーマには住所・エリア・位置情報のフィールドがなく、週次ジョブではブラウザの位置情報も使えないため、この入力が前提になる。未設定のユーザーと既存ユーザーは全体版のまま。(2) 既存の週次ダイジェストを、登録エリアとイベントタグで絞った版に切り替える(オプトイン、絞って 0 件なら全体版)。対象は `is_public` かつ `enterprise_id == null` のイベントに限る。
- **根拠:** CR01(中)。
- **成功指標:** 開封率・クリック率・ダイジェスト経由の申込比率、配信停止率。
- **前提:** F-12 と同じ在庫条件。公開範囲の未決事項([露出獲得施策 §11 #5/#6](../../13_成長・露出/01_露出獲得施策.md))。
- **工数:** M(エリア登録 UI とスキーマ追加を含む)。

## 6. 計測と判断基準

機能ごとの KPI(§5)とは別に、**ループ全体の指標**を月次で追う。目標値は実績が出るまで置かず、まずベースラインを取る([グロースストーリー §(e)](../10_概観/02_グロースストーリー.md) の指標案と整合)。

| 指標 | 定義 | 対応する柱 |
| :-- | :-- | :-- |
| 経路別の申込比率 | 注文確定を、招待・共有・ダイジェスト・発見・直接・検索に分けた比率 | 柱 0 |
| 招待の k | 1 申込あたりの招待経由の新規申込数 | 柱 1 |

| 開催成立率 | 公開イベントのうち最小催行人数を満たした割合 | 柱 2・3 |
